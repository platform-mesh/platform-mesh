# Adding a New Service to PlatformMesh

This guide walks through the end-to-end process of adding a new service to the PlatformMesh platform. A "service" is any workload managed by the platform-mesh-operator — it can be a backend API, UI frontend, controller/operator, or infrastructure component.

## Overview

A service in Platform Mesh consists of

- its **source code and container image**, built from this repository
  (`operators/` or `services/`) or from another repository (e.g. the portal),
- a **Helm chart** under `charts/`, which deploys the image,
- an entry in the **PlatformMesh profile**, which tells the platform-mesh-operator to install it.

The OCM components that tie chart and image together are generated by the
release tooling from the chart's `Chart.yaml`; there is nothing to write by
hand unless the chart deviates from the default shape (see Step 3).

## Step 1: Create the Helm Chart

### Directory Structure

Create a new chart under `charts/<service-name>/`:

```text
charts/my-service/
├── Chart.yaml
├── values.yaml
├── templates/
│   ├── deploy.yaml
│   ├── service.yaml
│   ├── sa.yaml
│   └── httproute.yaml    (if the service exposes an HTTP API)
└── tests/
    └── __snapshot__/
```

### Chart.yaml

Declare a dependency on the `common` library chart:

```yaml
apiVersion: v2
name: my-service
description: A Helm chart for my-service
version: 0.0.0
appVersion: 0.0.0
dependencies:
  - name: common
    version: 0.0.0
    repository: file://../common
```

- `version` is always `0.0.0` in git. Platform Mesh has one version; the
  release tooling writes it into every chart at build time
  (see [docs/release/process.md](../release/process.md)).
- `appVersion` is the container image tag:
  - `0.0.0` if the image is built from this repository (it becomes
    `vX.Y.Z`, the Platform Mesh version),
  - the image's own version if it is built in another repository (bumped when
    that repository releases),
  - `0.0.0` if there is no image (chart-only).
- Dependencies on charts in this repository are `file://` references with
  version `0.0.0`.

### values.yaml

Use the structure expected by the `common` chart helpers:

```yaml
image:
  name: ghcr.io/platform-mesh/my-service
  pullPolicy: IfNotPresent

port: 8080

deployment:
  resources:
    limits:
      memory: "512Mi"
    requests:
      cpu: "40m"
      memory: "50Mi"
```

### Templates

Use helpers from the `common` chart in your templates:

- `{{ include "common.entity.name" . }}` — consistent naming
- `{{ include "common.image" . }}` — image reference with tag
- `{{ include "common.healthAndReadiness" . }}` — liveness/readiness probes
- `{{ include "common.deploymentBasics" . }}` — replicas, strategy, selectors
- `{{ include "common.resources" . }}` — resource limits/requests
- `{{ include "common.basicEnvironment" . }}` — standard env vars

See `charts/common/templates/` for the full list of available helpers.

### If Your Service Has CRDs

Create a separate CRD chart `charts/my-service-crds/` and reference it as a conditional dependency:

```yaml
# In charts/my-service/Chart.yaml
dependencies:
  - name: common
    version: 0.0.0
    repository: file://../common
  - name: my-service-crds
    version: 0.0.0
    repository: file://../my-service-crds
    condition: crds.enabled
```

If the CRD is generated from Go types in this repository, do not copy it by
hand: add a `sync` line for it to
[`hack/charts/sync-crds.sh`](../../hack/charts/sync-crds.sh). `task generate`
then writes the chart copy from the component's `config/` output, and CI fails
when the two drift apart. Chart-specific templating (`spec.scope` from values,
an optional conversion strategy) is done by the script's transforms.

### Run Tests and Generate Docs

```sh
helm dependency update charts/my-service
helm unittest charts/my-service           # or: task helmtest-update
task charts:docs                                  # regenerate README from values.yaml
```

## Step 2: Container Image

**Built from this repository:** add the component to
[`ocm/components.yaml`](../../ocm/components.yaml) (path, image name, chart).
CI and the release workflows pick it up from there: every Platform Mesh
release builds the image at the release's version and publishes it together
with the OCM component `github.com/platform-mesh/images/my-service:X.Y.Z`
(see [docs/release/process.md](../release/process.md)). The `chart:` entry is
what tells the tooling to write the release version into the chart's
`appVersion`.

**Built elsewhere:** the other repository must publish the image and an OCM
component `github.com/platform-mesh/images/<name>:<version>` to
`ghcr.io/platform-mesh` (the portal does this today). The chart's `appVersion`
selects the version; bump it (manually or via Renovate) when a new image is
released. It must match an existing image component version, otherwise a
Platform Mesh release fails with a list of missing components.

## Step 3: OCM Component

Nothing to do for the common case. The release tooling derives from
`charts/my-service/Chart.yaml`:

```
github.com/platform-mesh/my-service:X.Y.Z
  ├─ chart → github.com/platform-mesh/helm-charts/my-service:X.Y.Z
  └─ image → github.com/platform-mesh/images/my-service:X.Y.Z      (built here)
                                                       :<appVersion>  (built elsewhere; omitted when 0.0.0)
```

If the chart deploys third-party images (like `infra` or `keycloak-operator`),
needs additional component references, or must not get an OCM component at all
(library charts), create `ocm/charts/my-service.yaml` — see
[`ocm/charts/README.md`](../../ocm/charts/README.md).

To make the service part of a Platform Mesh release, add a reference to the
aggregate in [`ocm/component-constructor.yaml`](../../ocm/component-constructor.yaml):

```yaml
      - name: my-service
        componentName: github.com/platform-mesh/my-service
        version: ${VERSION}
```

The reference `name` is what the PlatformMesh profile uses as `referencePath`
(Step 5); it is a contract once released.

## Step 4: CI

Nothing to set up. For components listed in `ocm/components.yaml`,
[`go-lint.yml`](../../.github/workflows/go-lint.yml) and
[`test.yml`](../../.github/workflows/test.yml) run the Go checks and tests of
the changed ones, [`helm-lint.yml`](../../.github/workflows/helm-lint.yml)
lints and tests the changed charts, and
[`verify.yml`](../../.github/workflows/verify.yml) checks the commits and that
all generated files are committed.

## Step 5: Profile / PlatformMesh Resource Configuration

Add your service to the installation profiles the operator chart ships:
`charts/platform-mesh-operator/files/kind-profile.yaml` and
`charts/platform-mesh-operator/files/production-profile.yaml`.

### Service Declaration

Add under `components.services`:

```yaml
my-service:
  imageResources:
    - annotations:
        repo: oci
        artifact: image
        for: my-service
  syncWave: 4
  enabled: true
  values:
    # Service-specific Helm values overrides
    hostAliases:
      enabled: true
```

### Configuration Fields

| Field | Description |
| ----- | ----------- |
| `enabled` | Enable/disable the service |
| `syncWave` | Deployment order (1=first, 4=last). Use lower waves for dependencies |
| `imageResources` | OCM image resources to track for image tag injection |
| `values` | Helm values overrides passed to the chart |
| `external` | `true` if the component lives outside this repo's OCM hierarchy |
| `helmRepo` | `true` if deployed from an external Helm repository (not OCM) |
| `targetNamespace` | Override the deployment namespace |
| `dependsOn` | List of services that must be ready before this one deploys |
| `absoluteReferencePath` | Path within the OCM component tree to find this service's chart |
| `suspend` | `true` to create the HelmRelease in suspended state (unsuspended by the operator when image resources are processed) |

### Deployment Ordering

The ordering mechanism depends on the deployment technology:

**ArgoCD**: Uses `syncWave` to control deployment order. Lower waves deploy first:

- **Wave 1**: Infrastructure operators (kcp-operator, cert-manager)
- **Wave 2**: Core platform (platform-mesh-operator)
- **Wave 3**: Supporting infra (infra chart with Keycloak, CNPG, networking)
- **Wave 4**: Application services (iam-service, portal, your service)

**FluxCD**: Uses a suspend/unsuspend mechanism. HelmReleases are created in a suspended state and the platform-mesh-operator unsuspends them once the corresponding image resources have been processed. Set `suspend: true` in the profile to opt into this behavior.

### Dependencies

If your service needs another service to be ready first:

```yaml
my-service:
  dependsOn:
    - name: infra
      namespace: platform-mesh-system
  # ...
```

### Templating & Value Substitution

The profile is the single place where values are pushed down into each child chart. Understanding
where each value comes from — and *when* it is substituted — avoids duplicating configuration.

#### Per-service `values:` are merged into the child chart

Everything under a service's `values:` block is deep-merged into that service's Helm chart values by
the platform-mesh-operator. To override a child chart value, set it here rather than editing the
chart — for example, to change the portal's cookie domain you set `portal.values.cookieDomain`, not
a chart default.

#### `{{ .baseDomain }}` / `{{ .baseDomainPort }}` — rendered by the operator

These are Go-template placeholders rendered by the platform-mesh-operator **at reconcile time**, from
`spec.exposure` on the PlatformMesh CR
(`charts/platform-mesh-operator/templates/installation.yaml`):

```yaml
spec:
  exposure:
    baseDomain: "portal.localhost"
    port: 8443
    protocol: "https"
```

| Placeholder | Renders to | Derived from |
| ----------- | ---------- | ------------ |
| `{{ .baseDomain }}` | `portal.localhost` | `spec.exposure.baseDomain` |
| `{{ .baseDomainPort }}` | `portal.localhost:8443` | `baseDomain` + `:` + `port` |

These are the **only two** template variables the operator exposes. Prefer them over hardcoding the
domain so the base domain is configured once in `spec.exposure` and flows to every service. Values
that are not just the base domain — the `hostAliases` IP (`10.96.188.4`), dev-server ports such as
`localhost:4200`, wildcard hosts (`*.portal.localhost`), and SMTP addresses — have no template
variable and must stay concrete.

#### `${org-name}` / `${org-subdomain}` — resolved by the portal at runtime

These are **not** substituted at build time. They pass through the operator's render and Helm
untouched and are resolved by the portal per organization at request time. Leave them as literal
`${...}` in the profile.

## Step 6: Testing

Install Platform Mesh on kind as described in [`installation/README.md`](../../installation/README.md),
with the `platform-mesh-operator` chart from your working tree
(`helm upgrade --install platform-mesh-operator charts/platform-mesh-operator ...`) so the profile
change is picked up, and `ocm.version` set to a published version that contains your chart — a
prerelease from your branch (`docs/release/process.md`, "Prereleases") until the chart is part of a
release. Then:

```sh
kubectl get helmreleases -A | grep my-service
kubectl get pods -n platform-mesh-system | grep my-service
```

## Checklist

- [ ] **Chart** under `charts/my-service/` (`version: 0.0.0`), `README.md.gotmpl`, tests, docs generated (`task charts:docs`)
- [ ] **Component registered** in `ocm/components.yaml` (if built here), or **`appVersion`** pointing at an existing `github.com/platform-mesh/images/my-service` version (if built elsewhere)
- [ ] **Aggregate reference** added to `ocm/component-constructor.yaml`
- [ ] **`ocm/charts/my-service.yaml`** if the chart deviates from the default shape
- [ ] **Profile entry** in the PlatformMesh default profile with the matching `referencePath`
- [ ] **Tested locally** (see `installation/README.md` for the kind setup)
